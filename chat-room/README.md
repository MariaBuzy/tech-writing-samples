# Chat API — OpenAPI Specification

Учебный проект с OpenAPI-спецификацией чат-сервиса. Спецификация описывает работу с чат-комнатами, участниками и сообщениями, а для получения новых сообщений использует Long Polling, то есть сервер может удерживать запрос открытым до появления новых данных или до истечения таймаута.

## Что описывает проект

Спецификация покрывает типовые операции чат-приложения:

- создание чат-комнат;
- добавление и удаление участников;
- отправку сообщений;
- получение новых сообщений через Long Polling.

Основная цель проекта — формально зафиксировать контракт между клиентом и сервером, чтобы поведение API можно было однозначно реализовать и проверить. Для long polling это особенно важно, потому что клиент должен понимать, когда сервер отвечает сразу, когда ждёт новые данные и что возвращает при истечении таймаута.

## Особенности API

### Long Polling для сообщений

Эндпоинт `GET /rooms/{roomId}/messages` реализован как long polling-запрос. Сервер удерживает соединение открытым до появления новых сообщений после момента `since` или до истечения `timeoutSeconds`.

Поведение ответа:

- `200 OK` — появились новые сообщения, сервер возвращает массив `Message`.
- `204 No Content` — за время ожидания новых сообщений не появилось, тело ответа отсутствует.
- `401 Unauthorized` — отсутствует API key или передан некорректный ключ.
- `403 Forbidden` — пользователь аутентифицирован, но не состоит в чат-комнате.
- `404 Not Found` — чат-комната не найдена.

Пример запроса:

```http
GET /rooms/10/messages?since=2026-04-27T10:00:00Z&timeoutSeconds=30 HTTP/1.1
X-API-Key: your-api-key
```

### Отправка сообщений

Эндпоинт `POST /rooms/{roomId}/messages` предназначен для отправки сообщения от аутентифицированного пользователя. Автор сообщения не передаётся в теле запроса, а определяется сервером по API key, поскольку передача идентификатора автора со стороны клиента позволяет подменять отправителя.

Пример тела запроса:

```json
{
  "text": "Hello chat!"
}
```

Возможные ответы:

- `201 Created` — сообщение успешно создано и возвращено в теле ответа.
- `401 Unauthorized` — пользователь не аутентифицирован.
- `403 Forbidden` — пользователь не является участником комнаты.
- `404 Not Found` — указанная комната не существует.

## Аутентификация и доступ

API использует аутентификацию по API key. Для таких схем ключ обычно передаётся в заголовке запроса, а не в query string или теле запроса, поскольку это безопаснее и соответствует распространённой практике документирования API.

Разделение ошибок `401` и `403` в спецификации принципиально важно:

- `401` означает, что клиент не прошёл аутентификацию;
- `403` означает, что аутентификация прошла, но доступ к ресурсу запрещён.

Дополнительно для операций чтения и отправки сообщений зафиксировано бизнес-правило: пользователь должен быть участником чат-комнаты. Это делает контракт API полным не только на уровне HTTP, но и на уровне предметной логики приложения.[8]

## Структура запросов и моделей

Ключевая модель для отправки сообщения — `CreateMessageRequest`. После исправления она содержит только поле `text`, потому что автор сообщения вычисляется на сервере по контексту аутентификации, а не задаётся клиентом напрямую.[6]

Пример схемы:

```yaml
CreateMessageRequest:
  type: object
  description: |
    Данные для отправки сообщения.
    Автор определяется на сервере по API ключу.
  properties:
    text:
      type: string
      example: "Hello chat!"
  required:
    - text
```

Такой подход уменьшает риск некорректных или небезопасных запросов и лучше соответствует хорошим практикам проектирования OpenAPI-спецификаций.

## Как использовать спецификацию

1. Открыть файл спецификации в Swagger Editor или другом OpenAPI-совместимом инструменте.
2. Проверить корректность схем, параметров и кодов ответов.
3. Использовать спецификацию как контракт для реализации клиента и сервера.
4. Отдельно протестировать сценарии long polling: появление новых сообщений, таймаут ожидания, ошибки аутентификации и запрет доступа.

## Что важно проверить при защите

При демонстрации проекта стоит отдельно пояснить следующие решения:

- почему `GET /rooms/{roomId}/messages` — это именно long polling, а не обычная фильтрация по времени;
- почему при отсутствии новых сообщений возвращается `204 No Content`;
- почему `authorId` убран из `CreateMessageRequest`;
- почему в защищённых операциях явно указаны `401` и `403`.

## Технологическая основа

Проект ориентирован на OpenAPI как на формат описания HTTP API. Хорошо оформленная спецификация упрощает валидацию контракта, генерацию документации и согласование поведения между клиентом и сервером.
